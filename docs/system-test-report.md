# MorphLake 系统测试报告（第三轮：真实组件链路验证）

- 测试日期：2026-09-03
- 被测对象：GitHub `schoIarw/morphlake`，目标提交 `574854ae3486477ee2187d0f56c474e5b5659b8c`（feat: scale multimodal storage to four Paimon tables）

- 测试性质：系统测试（真实 MinIO + 宿主机 Ollama + Docker 容器链路，非 Mock）

## 执行摘要

本轮在真实组件链路上按 12 个阶段顺序执行系统测试：代码基线、环境连通、自动建表、三模态上传、四表数据校验、清单/全文/向量/下载、索引时效、异常补偿、重启恢复、分页正确性、小并发基线、1 亿/日容量差距分析。

功能主干（上传、四表写入、跨表一致性、异常回滚、重启恢复、图片/音频向量召回、下载）全部按预期工作，未发现孤立数据或对象丢失。但发现 4 项影响对外可见行为的缺陷：

1. **DEF-01（严重）向量检索不按相似度排序**——返回结果按行 ID 升序，`rank` 仅为列表位置编号，未使用索引相似度分数。
2. **DEF-02（严重）全文检索缓存陈旧**——长驻进程中新上传内容分钟级（实测最长 8 分钟以上）不可见，重启服务后恢复。
3. **DEF-03（致命）清单分页 offset 完全失效**——数据量超过 limit 时所有页返回相同内容（全表最旧的 limit 行），跨页重复、中间页不可达，客户端遍历必然漏数据。
4. **DEF-04（严重）健康检查无法发现索引失效**——索引维护线程持续抛异常期间 `/health/ready` 仍返回 200 OK。

另有 2 项已量化的架构限制：单容器单 worker 同步模型调用导致上传吞吐不随并发扩展（1c/4c/8c 均约 1.8 files/s）；索引维护周期（30s）造成上传延迟周期性尖峰（0.6s→2.9s）。以实测吞吐外推，与 1 亿文件/日目标差距 3～4 个数量级。

26 项单元测试通过不能覆盖上述任何一项缺陷；本轮结论为系统测试**不通过**。

### T10 分页正确性（不通过）

- 输入：37 条清单数据，分别以 limit=5/10/16 全量翻页（脚本 `test-artifacts/st2-pagination.sh`）。
- 预期：各页并集等于全集，无重复无遗漏。
- 实际：
  - limit=5：8 页全部返回**相同的 5 条记录**（fetched=37, unique=5, 重复 32 次）；limit=10、limit=16 同样如此。
  - 域过滤分页同样失效（`business_domain=st1` 21 条，limit=5 的 4 页内容完全相同）。
  - 模态过滤下出现跨页重复（`media_type=image` 7 条 limit=3：offset=0 与 offset=3 页均含同一 file_id；offset=3 与 offset=6 页完全相同）。
  - 边界行为：offset=37（等于总数）返回空；limit=201 与 offset=-1 正确返回 422。
- 根因（已定位到代码与库行为叠加）：`paimon_store.list_assets` 以 `with_limit(limit+offset)` 读取底层扫描**前 limit+offset 行**（实测底层按 created_at 升序返回最旧 N 行），再在应用层按 `(created_at, file_id)` 降序排序后取 `rows[offset:offset+limit]`。数学上可证明：当总行数 > limit 时，任意页恒等于"全表最旧的 limit 行"，仅当 `offset+limit ≥ 总行数` 时才返回正确的尾部页。
- 证据：`test-artifacts/st2-pagination.sh`、`app-list-repro.py`、`slice-debug.py`（含原始行序、排序、切片全过程输出）。
- 结论：**不通过（DEF-03）**。深分页遍历会大量重复且永远无法到达中间页，对任何需要翻页的消费方均为数据正确性风险。

### T12 1 亿/日容量差距分析（分别计算）

**目标 A：1 亿文件/日（上传侧）** —— 需持续 1,157.4 files/s。

实测单容器吞吐（真实链路）：

| 负载类型 | 单请求耗时 | 单流吞吐 | 与目标差距 |
| --- | --- | --- | --- |
| 小文档（4.6KB，本轮实测） | 0.54s | 1.86 files/s | 622 倍 |
| 中文档（9 切片，v2 实测） | 2.54s | 0.39 files/s | ~2,968 倍 |
| 大文档（213 切片，v2 实测） | 15.31s | 0.065 files/s | ~17,806 倍 |
| 图片（minicpm-v 描述+nomic 向量化，v2 实测） | 11.3～32.7s | ~0.05 files/s | ~23,148 倍 |
| 音频（hash 向量，v2 实测） | 0.52～1.56s | ~1.0 files/s | ~1,157 倍 |

- 并发不扩展（T11），上述单流数字即单容器有效上限；图片负载下需 ~2.3 万个等效容器。
- 混合负载估算（40% 小文档/30% 图片/30% 音频，加权 6.9s/文件 → 0.145 files/s）：差距 ~8,000 倍。
- 瓶颈构成：同步模型调用占上传耗时主体（小文档 0.54s 中 Ollama embed 为主；图片两段模型调用 11～33s），其次为单 worker 事件循环/线程池串行化；MinIO 与 Paimon 写入本身在当前规模未构成瓶颈。

**目标 B：1 亿 Paimon 行/日（存储/索引侧）** —— 需持续 1,157.4 rows/s。

- 实测行生成率（文本主导）：1.86 files/s × 实测平均 26 行/文件（st1：235 text 行 / 9 文件）≈ **48 rows/s**，差距 **~24 倍**；该吞吐受制于同一模型调用瓶颈，非 Paimon 写入本身。
- 纯写入路径估算：剔除模型调用后每文件 ~0.15s（MinIO put + Paimon commit），约 6.7 files/s ≈ 174 rows/s，单容器仍差 ~6.6 倍，需多容器水平扩展（前提是先解除模型串行化）。
- **索引维护**：当前 <600 行规模下，单轮 IVF-SQ 维护在秒级（由尖峰 2～3s 推断），周期 30s 尚可跟随。IVF-SQ 训练（k-means 量化）成本随行数超线性增长，1 亿行量级下单轮构建将远超 30s 周期，索引滞后将**无限累积**——这是与目标 B 最根本的结构性差距。
- **检索路径**：清单接口为底层截断读取 + 应用层全量内存排序（且已因此产生 DEF-03），O(n) 复杂度在 1 亿行上不可用；全文检索依赖的缓存视图同样需要全表量级刷新。
- 结论：以当前架构（单容器单 worker、同步模型调用、30s 全量索引周期、O(n) 读路径）无法通过水平加机器直接达成 1 亿/日，需模型服务批量化/异步化、增量索引、游标分页与读路径下推等架构级改造。

## 风险清单

- R1 大规模下 IVF-SQ 索引维护周期无法跟随写入速率，索引滞后累积，向量检索时效持续劣化（T12）。
- R2 生产环境无重启自愈手段时，DEF-02 将导致全文检索长期不可见新数据。
- R3 任何翻页消费方（同步任务、导出、对账）受 DEF-03 影响产生静默漏数据。
- R4 索引失效静默（DEF-04）叠加 DEF-01，检索质量退化不可观测，无法触发告警。
- R5 模型层为单点同步调用（LIMIT-01），水平扩容容器无法提升吞吐，容量规划需以模型服务改造为前提。
- R6 历史旧表与现行四表并存于同一 warehouse，跨轮次数据治理与命名规范缺失，长期运行易误读（T9 对账时 21 个历史对象需人工甄别）。

## 最终结论

**不通过。**

依据：本轮为真实组件链路系统测试，主干功能与数据一致性达标，但存在 1 项致命缺陷（DEF-03 分页失效）与 3 项严重缺陷（DEF-01/02/04），其中 DEF-02 与 DEF-04 已在真实运行日志中取得直接证据。检索可见性、检索语义、分页正确性与可观测性均不满足系统测试出口准则；26 项单元测试全部通过的事实不能改变上述结论。建议优先修复 DEF-03（读路径排序/分页下推）与 DEF-02（缓存失效机制），并以 DEF-04 补齐索引健康度检查后复测。
